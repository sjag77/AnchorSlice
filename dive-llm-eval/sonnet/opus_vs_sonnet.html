Opus 5 vs Sonnet 5 on the AnchorSlice benchmark

Same 50 DIVE contracts, same calibrated prompt and JSON schema, one call per contract. Each model was run on the complete source (full) and on the AnchorSlice output (sliced). Scores are against the DIVE labels (400 label cells, 119 positives).

Update: Opus was rerun on 20 new contracts with a fresh cache and merged with the 50 (70 contracts). With clean token counts, slicing saves about 23% of tokens and cost. Over the 70 contracts, detection is unchanged (McNemar p = 1.00). Details are in the first section below.

DetectionOpus is ahead. Opus sliced is the best run (F1 0.500, recall 0.630). Sonnet reaches F1 0.38 with or without slicing.
Slicing helps Opus, not SonnetSlicing raised Opus's F1 by 7.3 points but left Sonnet flat (−0.9). Neither change is statistically significant (p = 0.76 and 0.74).
CostSonnet costs about 37% less ($2.09–2.15 vs $3.36–3.41) but is slower, because it writes about twice as many output tokens.
Token savings are smaller than reportedSonnet's token total fell only 7.6% with slicing, against 56.6% for Opus. The Opus figure is inflated by cache reads; see below.

Update: Opus on 20 new contracts, then merged to 70

20 new DIVE contracts (seed 20260922, none shared with the earlier 55) were selected with at least 2 positive and 2 negative contracts per category. Before any model call, the slicer kept evidence for 43/43 labelled vulnerabilities (every category 1.00) at 49.0% of source characters. The two Opus arms were then run one after the other with a fresh cache. Every call read the same 3,324 cached prompt tokens, so these token counts are clean.

What the new contracts show. On the 20 new contracts, slicing cost Opus 2 true positives (F1 −2.5 points), the opposite direction from the 50-contract sample. Over all 70 contracts, slicing still improves recall (+9.9 points) and F1 (+4.3), but the paired test is flat: 27 cells were correct only with full source and 28 only with slicing (McNemar p = 1.00). The honest claim is now "slicing does not change detection quality", not "slicing improves it". In the merged set, access control (+8.6) and front running (+7.1) still gain and DoS still loses (−12.9).

Token cost, measured cleanly. On the new contracts, slicing saved 23.7% of tokens and 22.8% of cost. This is the defensible figure. The merged −49.4% still includes the cache-inflated 50-contract full-source run, so it should not be quoted.

Why the token savings differ. Every Sonnet call used exactly 2 turns and read the same 3,299 cached prompt tokens, so its token counts are clean. On the part that actually depends on the contract (cache writes), slicing cut Sonnet's input by 22.8% (248,322 → 191,703), but output grew 15%, leaving a total saving of 7.6%. Opus full read a median of 13,916 cached tokens per contract, and some calls took 3 turns. That suggests the contracts were already cached from an earlier run and some calls retried. So most of the paper's 56.6% saving comes from cache reads rather than from fewer contract tokens. Before submitting, rerun the Opus arms back-to-back from a cold cache, or report input tokens excluding cache reads.

The main difference between the models is how conservative they are. Sonnet flags far less reentrancy (12 vs 23) and arithmetic (12 vs 17). The MUTFN access-control tag that lifted Opus from 6 to 17 positives had no such effect on Sonnet (9 → 6). Sonnet also ignored the over-broad DoS tag that misled Opus (11 → 11 vs 13 → 20). Both models over-call front running on almost every contract.

No difference reaches significance. The two models agree with each other on 90.5% of cells (full source), far more than either agrees with DIVE (about 61%). That echoes the earlier pilot: the models disagree with DIVE's labeling policy more than they disagree with each other.

What this means for the paper

1. Slicing never degraded detection significantly for either model, so the claim "input reduction does not harm detection" holds for both. 2. The improvement in effectiveness is specific to Opus and should not be generalised. 3. The token-saving figure needs a clean remeasurement before it goes into the paper: for Sonnet, slicing saves 22.8% of contract-dependent input and 7.6% overall.
