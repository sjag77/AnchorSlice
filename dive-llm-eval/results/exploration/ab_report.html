Static pre-slicing cuts tokens by 57% and does not cost accuracy

An A/B of the 50-contract DIVE evaluation, run twice under identical conditions. The only variable is a static regex pre-filter that removes lines matching no vulnerability anchor before the source reaches the model.

The pre-filter

What the two arms actually saw

Both arms use the same samples_50.json, the same system prompt, the same model and effort. Arm B replaces each contract's source with the output of slice.py: comments stripped, standard library constructs (SafeMath, IERC20, Ownable, IUniswap*) collapsed to a stub, and the remainder grouped into numbered blocks tagged with the DASP categories whose lexical anchors fired inside them. The model is told the tags are lexical hints, not findings.

Slicer validated against the DIVE labels before the run: every label-positive contract retains at least one block tagged with that category.

Access Control: the anchor did its job

The baseline marked only 6 of 39 positives. The slicer's MUTFN anchor — every public/external function that is not view or pure — tags exactly the entry points where a missing modifier would live, and the model found 11 more. False negatives fell 33 → 24 at a cost of 2 false positives.

DoS: the anchor was too generous

The DoS anchor includes require(, revert and assert(, which appear in nearly every function. Almost every block carries a DoS tag, and the model read the ubiquity as evidence: positives went 13 → 20 against a ground truth of 7, with false negatives unchanged at 3. The tag bought nothing and cost 14 points.

Why a 57% token cut is worth 1.4%

Two effects cancel. Output tokens — the most expensive class, and roughly half the bill — fell only 15.6%, because reasoning length is driven by the number of categories to judge, not by how much source there is to read. And the cheap 724k cache-read block was replaced by a 176k cache-write block that costs about 12× more per token. Slicing changed which tokens are spent more than how much they add up to.

Reading

What this run does and does not establish

  • Slicing is safe. Removing 40% of the source did not degrade agreement — the model was not using the discarded lines. That is the load-bearing result, and it holds independently of everything else here.
  • The accuracy movement is a bias shift, not a capability gain. Predicted positives rose 148 → 181 against a ground truth of 119. Recall bought 18 true positives and paid 15 false ones. κ improved because the baseline was badly under-predicting, not because the model reasons better on sliced code.
  • The tags are not neutral. Categories whose anchors fire everywhere (DoS, Front Running) drove the model toward positives regardless of the prompt's warning. An anchor that tags 90% of blocks carries no information and should not be shown.
  • Cost is not the reason to do this. 1.4% is noise. The defensible wins are 56.6% fewer tokens against a context limit and 19.7% less wall clock.
  • n = 50, single run. A 0.7 pp agreement delta on 400 cells is well inside run-to-run variance. Nothing here separates the two arms on raw agreement; the per-category movements (+14, −14) are the only shifts large enough to act on.

Next

Three changes worth testing

  • Drop require(, revert, assert( from the DoS anchor and re-check recall. If DoS recall survives on loop and external-call anchors alone, that alone should recover most of the 14-point loss.
  • Suppress tags above a coverage threshold. If a category tags more than ~60% of a contract's blocks, emit the blocks without that tag — it is noise, and the model treats it as signal.
  • Run the sliced arm without tags at all. That separates the two things this experiment currently confounds: the effect of removing code, and the effect of naming candidate categories. Given the token cut is safe, the tag-free variant is the cleaner default if it holds agreement.
