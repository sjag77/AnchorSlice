The slicer changes cut how often a tag fires without losing evidence: DoS 61% → 45% of blocks, Front Running 59% → 23%, Unchecked Return Values 40% → 29%. The prompt changes state, per category, what the benchmark actually marks — for example that a checked .call still counts for Unchecked Return Values in this corpus, that a bare require is not DoS, and that a sale window gated on block.number is labelled Bad Randomness.

False negatives fall from 74 to 28 while false positives fall from 139 to 75, so this is not a threshold trade: both error types drop together. By comparison, A against B is exactly flat (27 / 28, p = 1.00), which is why slicing alone was never a detection story.

The right reading is coverage, not a league table. DIVE's ground truth is the union of six analyzers, each of which ran on part of the corpus; no single tool answers every category on every contract, and two of the six contribute nothing here. A model-based detector reading a sliced contract reproduces that six-tool consensus on 82% of all cells and recovers 83% of its positives, at complete coverage, without any of the tools.

Slicing cuts the contract text the detector must read by about 36% (6,118 → 3,963 cached tokens per contract) and total input by 20–26%. Configuration C sits slightly above B because the calibrated prompt is longer and the model writes more justification, and it is slower per contract for the same reason. The slicer itself costs 7.6 ms per contract and needs no compilation.

The 56.6% token reduction in the current manuscript draft must be withdrawn: its full-source arm reused a warm cache (a median of 13,916 cached tokens read per contract, against 3,324 in a cold run), which inflates the baseline. Every figure on this page comes from cold-cache runs.

What the paper can claim

1. Evidence retention (RQ1). 162 of 162 labelled vulnerabilities retained across 70 contracts, 1.00 in every category, including 43/43 on contracts that played no part in developing the anchors. The slice keeps 55% of source characters and is produced in 7.6 ms without compiling.

2. Token efficiency (RQ2). About 22% fewer tokens and 22% lower cost per contract, and roughly 36% less contract text read, measured cold-cache with the detector and contracts held fixed.

3. Detection effectiveness (RQ3). Agreement with the DIVE reference rises from 0.620 to 0.816 and F1 from 0.452 to 0.722 (κ 0.173 → 0.588), with false negatives cut from 74 to 28 and false positives from 139 to 75; McNemar p < 0.0001. On the 55 contracts never used for tuning, F1 still rises from 0.378 to 0.633. Detection quality therefore improves while token cost falls — the two results together, which is the paper's thesis.

4. Coverage. Complete coverage of eight categories on all contracts, against 6–78% for the individual analyzers whose union defines the labels.

Limitations to state, and what to run next

The prompt rules describe how DIVE labels behave, not Solidity semantics: each category is effectively defined by whichever analyzer ran (Front Running comes only from Mythril; Time manipulation mostly from Solhint; Arithmetic mostly from VeriSmart, which ran on 6% of cells). Calibrating to that is legitimate and must be declared, and it limits transfer to other benchmarks. Three runs of one configuration varied by 4.2 points of agreement, so single-run differences below that are noise. Bad Randomness trades 4 misses for 16 false positives and Arithmetic is untouched — both are open. Before submission: a held-out run on fresh contracts from the archive, repeated runs for variance, and an Arithmetic rule derived the same way as the others.
